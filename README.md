# Redis Cache-Aside API

A .NET 8 Web API demonstrating the **cache-aside pattern** using Redis in front of a SQL Server database. Shows cache HIT/MISS logging, Redis-down fallback, and cache invalidation on write.

---

## Tech Stack

| Layer | Technology |
|---|---|
| Framework | .NET 8 Web API |
| Database | SQL Server (softsuave\SQLEXPRESS) |
| Cache | Redis (via StackExchange.Redis) |
| ORM | Entity Framework Core 8 |
| Auth | JWT Bearer |
| Docs | Swagger / Swashbuckle 6.9 |

---

## How to Run Locally

### Prerequisites
- .NET 8 SDK
- SQL Server (Express or LocalDB)
- Redis for Windows — install via:
  ```powershell
  winget install Redis.Redis
  ```

### Steps

1. **Clone / open the project**
   ```powershell
   cd D:\Redis\RedisCache.API
   ```

2. **Verify Redis is running**
   ```powershell
   & "C:\Program Files\Redis\redis-cli.exe" ping
   # Expected: PONG
   ```

3. **Update the connection string** in `appsettings.json` if your SQL Server instance differs:
   ```json
   "DefaultConnection": "Server=softsuave\\SQLEXPRESS;Database=RedisCacheDb;Trusted_Connection=True;TrustServerCertificate=True;"
   ```

4. **Run the API** — EF Core migrations run automatically on startup:
   ```powershell
   dotnet run --launch-profile https
   ```

5. **Open Swagger UI** in your browser:
   ```
   https://localhost:7268/swagger
   ```

## Authentication

All product endpoints require a JWT Bearer token.

1. Call `POST /api/auth/login` with:
   ```json
   { "username": "admin", "password": "admin123" }
   ```
2. Copy the `token` from the response.
3. Click **Authorize** (lock icon) in Swagger UI and paste the token.

## API Endpoints

| Method | Route | Description | Auth |
|---|---|---|---|
| POST | `/api/auth/login` | Get JWT token | No |
| GET | `/api/products` | Get all products | Yes |
| GET | `/api/products/{id}` | Get product by ID | Yes |
| POST | `/api/products` | Create a product | Yes |
| PUT | `/api/products/{id}` | Update a product | Yes |
| DELETE | `/api/products/{id}` | Delete a product | Yes |

### POST /api/products — Request Body
`Id` is excluded from the request — it is auto-generated by the database.
```json
{
  "name": "Laptop",
  "category": "Electronics",
  "price": 999.99,
  "stock": 15
}
```

## Key Design Decisions

### Cache Key Naming
| Key | Covers |
|---|---|
| `product:{id}` | Single product by ID |
| `products:all` | Full product list |

Namespaced keys make it easy to identify and query them in RedisInsight or redis-cli.

### TTL (Time-To-Live)
Set to **5 minutes** for both keys.

Product data is stable enough to cache for several minutes, but short enough that stale data does not persist long if explicit invalidation is missed. In production this would be tuned based on how frequently products change.

### Serialization
`System.Text.Json` — built into .NET, no extra dependencies needed.

### Redis Connection — Singleton
`IConnectionMultiplexer` is registered as a **singleton** because:
- Creating a Redis connection is expensive
- `IConnectionMultiplexer` is thread-safe by design
- One shared connection serves all HTTP requests for the app lifetime

### Invalidation Strategy — Invalidate on Write
When a product is updated or deleted:
- The `product:{id}` key is deleted from Redis
- The `products:all` key is also deleted
- The next read triggers a fresh DB query and re-populates the cache

This guarantees the next read always returns fresh data without waiting for TTL to expire.

### Redis Fallback
Every Redis operation is wrapped in `try/catch`. If Redis is unavailable:
- A `Warning` log is written: `!!! REDIS DOWN — FALLING BACK TO DATABASE`
- The request continues and hits SQL Server directly
- The API **never crashes** due to Redis being down

Connection timeout is set to **500ms** so the fallback is fast and the user experience is not impacted.

## Demonstrating the Cache-Aside Flow

### Scenario 1 — Cache HIT / MISS

```
GET /api/products
  → CACHE MISS — key: products:all | Fetching from DB...
  → CACHE SET  — key: products:all | 2 products cached | TTL: 5 mins

GET /api/products (again)
  → CACHE HIT  — key: products:all
```

### Scenario 2 — Redis Down Fallback

```powershell
Stop-Service Redis
```
```
GET /api/products
  → !!! REDIS DOWN — GET 'products:all' failed. FALLING BACK TO DATABASE.
  → CACHE MISS — key: products:all | Fetching from DB...
  (returns 200 OK — app does not crash)
```
```powershell
Start-Service Redis
```

### Scenario 3 — Cache Invalidation

```
GET /api/products/1   →  CACHE MISS → stored in Redis
GET /api/products/1   →  CACHE HIT
PUT /api/products/1   →  CACHE INVALIDATED — keys: [product:1, products:all]
GET /api/products/1   →  CACHE MISS → fresh data from DB
GET /api/products/1   →  CACHE HIT
```

## Inspecting Redis Keys Live

```powershell
# See all cached keys
& "C:\Program Files\Redis\redis-cli.exe" keys *

# Read a cached value
& "C:\Program Files\Redis\redis-cli.exe" get "products:all"

# Check TTL remaining (in seconds)
& "C:\Program Files\Redis\redis-cli.exe" ttl "products:all"

# Manually delete a key
& "C:\Program Files\Redis\redis-cli.exe" del "product:1"
```

## Assumptions

- Credentials (`admin` / `admin123`) are stored in `appsettings.json` — acceptable for a learning project, not for production.
- `GetAll` caching uses a single `products:all` key. Any Create, Update, or Delete invalidates this key entirely since partial list invalidation would require tracking individual IDs.
- Redis runs on the default port `6379` with no password (development setup).
